# Auth and Tenants (API) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add accounts, sessions, email verification, password reset, tenants, and email invites to the `dearest` API.

**Architecture:** A server-side session in an `HttpOnly` cookie identifies the user. A middleware loads the session for each request. Extractors enforce login, the verification gate, and tenant membership. Tenant routes have the tenant ID in the path. Email goes through an `EmailSender` trait. The production implementation uses SMTP (Resend). A recording implementation serves the tests.

**Tech Stack:** Rust 1.99.1 (edition 2024), axum 0.8, SeaORM 2 with Postgres 18, `argon2`, `sha2`, `rand`, `base64`, `lettre`, `governor`, `tokio-util`, `axum-extra` (cookies), `uuid`, `chrono`.

**Spec:** `docs/superpowers/specs/2026-11-14-auth-design.md`

The web app has its own plan: `dearest.rsvp-web/docs/superpowers/plans/2026-11-14-auth-web.md`. It depends on the API contract in this plan.

## Global Constraints

- All IDs are UUIDs (`Uuid::now_v7()`). All times are `timestamptz` (`chrono::DateTime<Utc>`).
- JSON fields use `snake_case`. An error body is `{"error": "<code>"}`.
- Store emails lowercase and trimmed. Normalize every email input with `normalize_email` before any read or write.
- Passwords: argon2id, 19 MiB memory (`19456` KiB), 2 iterations, 1 lane. Run the hash and the check in `tokio::task::spawn_blocking`. The only password rule: not empty.
- Tokens: 32 random bytes from `rand::rngs::OsRng`, base64url without padding. The database stores only `SHA-256(token)` as `bytea`.
- Lifetimes: session 30 days (renew at most one time each hour), verification 24 hours, reset 1 hour, invite 7 days.
- Cookie: name `dearest_session`, `HttpOnly`, `Secure` (unless `COOKIE_SECURE=false`), `SameSite=Lax`, `Path=/`, no `Domain`, `Max-Age` 30 days.
- A non-member gets `404` on a tenant route, the same as for a tenant that does not exist.
- An unverified user gets `403 {"error":"email_not_verified"}` on every route that the spec marks "Unverified: no".
- Send email only after the transaction commits, through `state.tasks.spawn(...)`. A send failure never fails the request.
- Axum 0.8 path syntax is `/{param}`, not `/:param`.
- Add dependencies with `cargo add <crate>` (with features where this plan names them) so that the lockfile picks current versions.
- The database table for memberships is `user_tenant_memberships`.

## Review Focus

1. **Email case and spaces.** `" Alex@Example.COM "` at signup, then `alex@example.com` at login, at password reset, and in an invite, must all find the same account. Test: Task 5 `login_ignores_email_case_and_spaces`, Task 10 `invite_matches_email_case_insensitively`.
2. **A verification link clicked two times.** Email clients and link scanners open links. The second call must return `400 invalid_token` and must not change the user. Test: Task 6 `verify_twice_returns_invalid_token`.
3. **An invite accepted by a user who is already a member** (from a second invite, or two clicks). The API must not create a second membership row and must not return `500`. Test: Task 10 `accept_when_already_member_returns_409`.
4. **An old session after a password reset.** A browser that kept a cookie from before the reset must get `401` on the next call. Test: Task 7 `reset_ends_all_sessions`.
5. **A logout or a password change in the same request as a session renewal.** The middleware must not put back a cookie that the handler cleared. Test: Task 5 `logout_clears_cookie_even_when_session_renews`.

**Interfaces:**
- Consumes: `AppState`, `AppError`, `TestApp` (Task 4), entities (Task 2), `templates::verification_email` (Task 3).
- Produces:
  - `password::hash_password(password: String) -> AppResult<String>`
  - `password::verify_password(password: String, hash: String) -> AppResult<bool>`
  - `password::verify_dummy(password: String) -> AppResult<()>`: checks against a fixed hash made one time in a `std::sync::LazyLock`. Login calls it for an unknown email.
  - `token::new_token() -> (String, Vec<u8>)`: (plain token, SHA-256 hash).
  - `token::hash_token(token: &str) -> Vec<u8>`
  - `validate::normalize_email(input: &str) -> AppResult<String>`: trim, lowercase. Return `InvalidInput` if the result is empty, longer than 254 characters, or does not have exactly one `@` with text on both sides.
  - `validate::validate_name(input: &str) -> AppResult<String>`: trim. 1 to 100 characters. Tenant names use the same function with a limit of 200: `validate::validate_text(input: &str, max: usize) -> AppResult<String>`, and `validate_name` calls it with 100.
  - `validate::validate_password(input: &str) -> AppResult<()>`: `InvalidInput` only if empty.
  - `session::create_session(db: &impl ConnectionTrait, user_id: Uuid) -> AppResult<String>`: inserts a row, returns the plain token.
  - `session::session_cookie(token: &str, secure: bool) -> Cookie<'static>` and `session::clear_cookie(secure: bool) -> Cookie<'static>`.
  - `session::load_session` middleware: reads the cookie, finds the session row by `hash_token`, ignores it if `expires_at <= now`, loads the user. It puts `Option<CurrentSession { session_id: Uuid, user: users::Model }>` into the request extensions. If `now - last_seen_at > 1 hour`, it sets `last_seen_at = now` and `expires_at = now + 30 days`, and after the handler runs it adds a fresh `Set-Cookie` with the same token, but only if the response does not already have a `Set-Cookie` for `dearest_session`.
  - Extractors in `extract.rs`:
    - `AnyUser(pub CurrentSession)`: `Unauthenticated` if there is no session.
    - `VerifiedUser(pub CurrentSession)`: as `AnyUser`, then `EmailNotVerified` if `email_verified_at` is null.
    - `MaybeUser(pub Option<CurrentSession>)`: never fails.
  - Helper `auth::send_verification(state: &AppState, user: &users::Model) -> AppResult<()>`: inside its own transaction, deletes the user's unused `verify_email` tokens, inserts a new one (24 hours), commits, then `state.tasks.spawn` sends `verification_email`. Task 6 uses it for resend.
  - Routes:
    - `POST /auth/signup {email, password, name}` returns `201` with the `me` body and a session cookie. `409 email_taken` if the email exists (also catch the unique violation from a race and map it to `EmailTaken`).
    - `POST /auth/login {email, password}` returns `200` with the `me` body and a cookie. `401 invalid_credentials` for an unknown email or a wrong password.
    - `POST /auth/logout` returns `204`, deletes the session row, sets `clear_cookie`. With no session, it still returns `204`.
    - `GET /auth/me` (`AnyUser`) returns `{"user": {"id", "email", "name", "email_verified": bool}, "memberships": [{"tenant_id", "tenant_name"}]}`, memberships sorted by tenant name.
